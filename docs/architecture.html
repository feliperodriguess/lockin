lockin · architecture & api map

How lockin talks to the League client, Riot's CDN, and itself.

lockin is an Electron companion for champion select. It reads the local League Client (LCU) over WebSocket + HTTPS, pulls static art from Data Dragon, stores your data locally, and performs exactly one automated write (accepting a ready check). This page traces every wire, end to end.

WebSocket push — live LCU events REST GET — reads REST POST — the only writes IPC invoke — request/response IPC push — main→renderer events DDragon CDN — static data + icons

01 The whole picture

Three Electron processes. Only the main process touches the network, the LCU, the filesystem, or the LCU's self-signed certificate. The renderer is pure UI and reaches main exclusively through the typed window.api bridge. Follow the colored arrows.

Solid = goes through main. Dashed = the two exceptions (disk I/O, and renderer-side icon hotlinking).

02 How to know every LCU endpoint

The LCU self-documents. The client serves its own machine-readable API spec on the same local port — no external reference needed. Newer builds expose GET /swagger/v3/openapi.json; on this build (patch 16.11) that's gone, but GET /Help returns the complete surface.

908 events

subscribable WebSocket topics (live pushes)

across 5 plugins — listed below. We read; we don't roam.

Try it yourself (token + port come from the running client's process args):

curl -sk -u "riot:$TOKEN" "https://127.0.0.1:$PORT/Help" | jq '.functions | length'   # → 1456
curl -sk -u "riot:$TOKEN" "https://127.0.0.1:$PORT/Help" | jq '.events | length'      # → 908

Community mirror of these specs (browsable, versioned): lcu-schema · Riot DTOs. But the on-client /Help is always the source of truth for your patch.

03 The LCU endpoints lockin actually uses

Nine calls, all in src/main/lcu.ts. Three are WebSocket subscriptions (the live heartbeat of the app); the rest are one-shot GETs on connect/refresh and the two POST writes.

Credentials come from league-connect's authenticate(), which scans the OS process list for LeagueClientUx and reads its --app-port + --remoting-auth-token flags. The LCU's cert is self-signed, so requests skip cert validation. All of this is main-process only.

04 Data Dragon — static art & catalog

Riot's free CDN of unchanging per-patch data (the *Static types). JSON is fetched + cached by main; the actual icons are hotlinked by the renderer's <img> tags — they don't need to round-trip through main.

TransportURLWhatWhere
GET/api/versions.json[0] is the latest patch — resolved firstddragon.ts
GET/cdn/{ver}/data/en_US/champion.jsonChampion catalog → championsByKey (key 266 = Aatrox)ddragon.ts
GET/cdn/{ver}/data/en_US/summoner.jsonSummoner-spell catalog → spellsByKey (key 4 = Flash)ddragon.ts
IMG/cdn/{ver}/img/champion/{file}.pngChampion portraits — loaded by the browser directlyddragon-urls.ts
IMG/cdn/{ver}/img/spell/{file}.pngSpell icons — loaded by the browser directlyddragon-urls.ts

Locale is a fixed en_US constant. The normalized bundle is written to userData/ddragon-cache.json and served cache-first: on launch it serves the cache instantly and, if the patch changed, refreshes the cache in the background for next launch. Offline with a cache → still works; offline with no cache → champ select renders fallback tiles instead of icons (never crashes).

05 What we store on disk

Two things live on disk, both under the app's userData folder. No backend, no cloud, no login — every byte is local.

electron-store config.json

Typed key→value store (src/main/store.ts). Three keys:

settingsAppSettings — autoAccept, autoAcceptDelayMs, spellSlotLayout (D/F), rankDiffThreshold
notesMatchupNote[] — your champion notes (body, opponent, pinned spells, timestamps)
banlistBanListEntry[] — prioritized personal ban list (championId, priority, reason)

Disk cache ddragon-cache.json

A plain JSON file (via node:fs, not electron-store) holding the normalized DDragonBundle for the current patch.

Why separate? It's a regenerable cache, not user data — it can be deleted any time and will re-fetch. Keeping it out of config.json keeps your real data small and clean.

Nothing else persists. No telemetry, no history, no account data.

06 Who owns which state in the renderer

Two homes, never duplicated. The rule: request/response data lives in TanStack Query; live LCU pushes live in React context. Small UI state stays in useState.

TanStack Query pull

Wraps the invoke channels. Cached, deduped, invalidated after mutations.

['ddragon'] · ['settings'] · ['notes'] · ['banlist'] · ['ranks',…]

LcuProvider context push

Subscribes once to the 4 push channels, split into two contexts by churn rate:

{ connected, phase } — changes a few times per queue
{ readyCheck, champSelect } — changes every WS tick

Components never call the bridge directly — they go through hooks (useChampSelect, useNotes, usePhase…). The four pure engines (notes-match, spells, bans, rank) are dependency-free functions that turn this data into what you see — and they're the only parts with unit tests.

07 The IPC contract — the one bridge

Every renderer↔main message is a typed method on the Api interface (src/shared/api.ts), exposed through contextBridge. The renderer imports no Node APIs and never hits the network itself.

lcu:acceptReadyCheck · lcu:declineReadyCheck

Each subscribe also delivers the current value immediately (via the snapshot), then streams updates.

08 End to end: a ready check, every hop

To make the wiring concrete, here's one event from the LCU all the way to a button on your screen — and back.

  1. LCU fires. You hit a queue pop. The client emits on /lol-matchmaking/v1/ready-check over the WebSocket lockin subscribed to at connect.
  2. Main maps it. LcuService receives the raw payload, maps it to the typed ReadyCheck, and — if auto-accept is on and you haven't declined — schedules the accept.
  3. Main pushes. It broadcasts lcu:readyCheck to the window via webContents.send.
  4. Provider catches it. LcuProvider's one subscription updates its context; useReadyCheck() re-renders only the components that read it.
  5. You see the countdown. The ready-check screen shows the ring ticking down (interpolated locally at 1 Hz between pushes).
  6. You click Accept. The button calls useAcceptReadyCheck() → lcu:acceptReadyCheck invoke → main.
  7. Main writes back. LcuService sends POST /lol-matchmaking/v1/ready-check/accept to the LCU. The loop closes — the LCU advances to champ select, which arrives as the next push.
